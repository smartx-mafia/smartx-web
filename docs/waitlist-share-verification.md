### 提交验证

- 沿用现有 `NEXT_PUBLIC_WAITLIST_API_BASE` 和 `Authorization: jwt <用户 token>`。
- 请求：`{ "postUrl": "https://x.com/example/status/123456789" }`。
- 沿用 `{ code, message, data }` 外层响应。
- `data` 为验证状态对象：

```json
{
  "status": "verified",
  "postUrl": "https://x.com/example/status/123456789",
  "xUser": { "id": "123", "username": "example" }
}
```

- 状态：`unverified | pending | verified | rejected`。`verified` 必须带真实 `xUser.id` 和 `username`。
- 拒绝时可返回 `status: rejected` 和 `reason`；错误响应的 `message` 也可使用同一机器错误码。
- 前端已支持：`INVALID_POST_URL`、`X_ACCOUNT_ALREADY_BOUND`、`INVITE_LINK_MISMATCH`、`POST_NOT_FOUND`、`POST_NOT_PUBLIC`、`POST_ALREADY_USED`、`RATE_LIMITED`、`SHARE_VERIFICATION_UNAVAILABLE`。未知错误显示通用提示，不原样暴露服务端文本。

### `/user/my_result` 必须调整

- 邮箱验证且已提交题目后立即返回完整 ResultCard，不再因 TG / X 未完成而只返回 `locked: true`。
- 同一响应新增 `shareVerification`（上述对象），供刷新、再次登录、验证中轮询恢复状态。
- `rank`：未验证返回 `null` / 不返回；只在 `shareVerification.status=verified` 时返回有效正整数名次。
- `verifiedInviteCount`：由服务端按下级分享验证成功统计的非负整数。

### 服务端建议验证顺序

1. 检查登录、请求格式、速率限制和幂等记录。
2. 提取 post ID 后通过 X 数据源获取真实帖子和真实作者 ID，不信任 URL 中的用户名，不任意抓取用户 URL。
3. 检查 X 是否已绑定其他用户；绑定本人应幂等返回。
4. 检查公开可访问性，以及帖子内展开后的 URL 是否为当前用户自己的 SmartX 邀请链接；按域名/路径/邀请码识别，兼容语言与分享图参数，不用简单子串匹配。
5. 所有校验成功后一次性提交绑定、验证状态、入榜与上级有效邀请事件。账号、帖子、邀请计数须有唯一性约束，禁止自邀与重复计数。

尚需服务端/产品决定：历史点击分享用户的迁移规则；删帖/改帖后的处理规则；允许原创、引用还是回复（普通转发不能仅因引用原帖有链接而通过）。
